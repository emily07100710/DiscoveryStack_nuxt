# Governed Live Publication Action V1

## Objective and boundaries

Complete the real server-owned publication-before / publication-after evidence path and admit reviewed actions into the existing observational content-effect learning workflow. A repository diff, remote HTTP 2xx, supplied checksum or marker alone is not live-page proof. This extension does not change the fixed outcome-contract-v1, evaluation-contract-v1 or primary consumer-AI citation contracts; action data is auxiliary, observational and never a primary citation label or causal result.

The runtime covers canonical first-party content pages whose server-rendered article follows the bounded live-content integration contract below. The existing publication public-URL resolver supplies the exact URL from the current owner/client/target and persisted identity; request JSON cannot supply URLs, HTML, consent, draft, target, receipt, status or features. An uninstrumented, client-only, inaccessible or not-yet-updated page remains unverified rather than being admitted. The reference Site Kit exposes an optional `buildFirstPartyLiveArticleProjection()` controlled article fragment and integration data; publishing transport acceptance is still separate from a customer's actual HTTP page/deployment and visual acceptance.

## Live HTML integration and semantic proof

- One canonical link must equal the exact server-resolved public URL. One article carries `data-ds-live-content="v1"` and exact publication, draft, review, content and evidence identity attributes. Its one marked title and one marked body contain actual server-rendered content, not an embedded unrendered copy of Markdown.
- Bounded semantic projection verifies the actual title/body against the approved draft representation as well as identity. Duplicate roots/attributes, invalid entities, hidden or active content, malformed structure, unsupported Markdown or oversized content fail closed. A marker with the correct content hash but different actual text does not pass.
- Projections retain only bounded hashes, indexes and numeric/structural signals. Raw HTML, title/body, URL, address, cookies, tokens and HTTP headers are transient, never persisted or returned. Pseudonymous hashes are not advertised as anonymous: automatic checks plus a distinct owner PII/rights review are required for learning admission.
- A known, same-URL HTTP 404 before publication is a new-page baseline, not an empty successful page. Existing pages without a verifiable controlled projection keep their before state unknown. Raw HTML proves HTTP-served semantics, not JavaScript execution, browser visibility, indexing or search/AI outcomes.

## Acquisition security and budgets

Only a current exact source authorization grants capture, independently of permission to publish. Current rights, source review, training terms, source PII state, same authorized origin, consent, revocation and retention are re-read before DNS/HTTP and after acquisition. Current robots policy must allow the exact page; authentication, robots denial, rate limiting and security interstitials are not bypassed.

Production GET uses an HTTPS transport with public DNS address validation and address pinning for the request while retaining hostname TLS verification. Only standard public HTTPS URLs without credentials, secret-like parameters or fragments are accepted. Redirects are not followed. DNS, authority reads, headers and streaming body share one hard wall-clock deadline; each response is at most 256 KiB. Only robots plus the single exact page are fetched, with one-second spacing. No credentials, cookie jar, provider SDK or arbitrary client fetch transport is used. Injected test transports are synthetic and do not validate a real customer site.

## Durable capture lifecycle

1. After the formal execute attempt is reserved under the existing publication lease and before the first write, resolve current owner/client/entry/draft/version/review/risk gate/target/public URL and exact learning authorization.
2. Create/replay one immutable action identity for that exact execute attempt. Capture and durably save the before projection and pre-write planned action features while the same publication attempt remains planned and the same live run lease is held. A restarted or already-dispatched attempt cannot invent a new before state after a possibly successful write.
3. Mark the actual publication-start boundary before dispatch. This marker is durable and compare-and-swap protected; recovery never recaptures a before image for an already-started attempt. Capture failure does not falsify business delivery; it leaves action learning blocked.
4. Revalidate the same planned publication attempt and current lease after acquisition, then re-read business review, job/draft/version/hash, risk gate and target configuration. Changed business authority stops dispatch; withdrawing learning consent alone does not revoke an independently approved business publication. Formal publication results still use the existing publisher identity checks and append-only attempt/event ledger. With the live-action path enabled, completion time comes from the server clock after transport, not from a pre-transport request timestamp; disabled-path legacy behavior is preserved.
5. Only a fresh exact formal delivered receipt authorizes after capture. The served canonical page must match the exact approved draft plus formal receipt identity. A stale page is deferred with bounded attempts/backoff; this path contains no publisher, generation, LINE or payment call.
6. The inline post-publication step verifies at most one delivered action, including in multi-target runs. Remaining actions or stale deployments are continued by an after-only recovery step: it selects at most 25 due rows and attempts at most one external after capture per learning tick. Partial multi-target receipts are usable only for their exact delivered target while the aggregate run is terminal; recovery of the failed publication target does not republish a delivered target. Durable CAS leases fence concurrent workers and stale completion. Captures/attempts and retention have fixed upper bounds. Failures never turn successful publication into re-publication.

Action storage is owner-scoped, bound to exact attempt/client/entry/run/draft/version/target/config/public-URL/authorization/source/content/evidence fingerprints, and separate from immutable business event payloads. Before/after JSON and planned features have a physical expiry: cleanup clears them under CAS and invalidates an active action lease; review history and non-private operational identity remain. Revocation/source drift blocks every use and cleanup clears derived projections. No production migration runs as a development side effect.

The reviewed migration also widens only the existing publication-attempt `completedAt` timestamp to millisecond precision. Existing timestamps retain their values; this is not rounding or fabricating historical delivery time. New live actions require a new exact before/dispatch/delivery chronology and do not backfill before evidence for historical publications.

## Review, release and learning

- Owner workspace shows only safe state, fingerprint, retention and reason codes. Review requires exact server-read evidence fingerprint, explicit PII review, rights confirmation and acknowledgement that this is observational, plus a hashed reason. Approval/rejection is immutable and owner-scoped; new evidence needs its own review.
- Every action release re-reads the current formal receipt, exact draft/target/public URL, exact current source authorization, evidence/checksum/review and preservation deadline. A checksum is never treated as an authority proof. Missing, changed, revoked or expired records cannot be exported or used by a model.
- A valid live after projection confirms the planned action observed at the controlled HTTP page. Training predictors come only from the before projection and the exact approved planned draft available before dispatch, never from follow-up metrics, later outcomes or a post-outcome after capture.
- Join action evidence to content-effect candidates using fresh exact formal publication receipt/entry/draft/target and current authorization, not a browser fingerprint. The action feature sidecar and its distinct review are included in immutable model-data approval and rechecked before/after CPU fitting and before every model use. Existing outcome-only artifacts retain their versioned validation; action-aware artifacts are explicitly versioned and never silently mutate historical approvals.
- The owner explicitly selects outcome-only V2 or reviewed-live-actions V3 before approving an immutable model-data release. The modes have separate lineage fingerprints and artifact validation. V3 adds ten bounded pre-dispatch action predictors, not after-observation features or follow-up metrics; an unavailable action release never falls back to V2 under a V3 approval. Fitted artifacts must match both the current publication-timing metadata and the current action sidecar. A validly rehashed wrong sidecar or a transplanted V2 artifact is not served as a V3 model.
- Existing minimum data, subject/time isolation, temporal holdout, train-only fitting, limits and independent production activation gates are retained. New-page/unknown before and action missingness stay explicit; auxiliary actions cannot create positive or negative outcome labels. Enough real data, provider/phone acceptance and production model quality remain separately gated.

## Default-off and owner routes

`NUXT_LEARNING_LIVE_ACTION_ENABLED` is server-only and defaults false. When false, the new pre/post capture path performs no action configuration/authority/DB/DNS/HTTP work; dry-run performs none regardless of the switch. Retention cleanup remains a separate opt-in under the existing learning-retention policy. No browser or task payload can enable execution. New owner operations use the existing intervention catch-all with same-origin POST, strict bounded bodies, no-store/noindex and session-derived owner identity; no new route file or public CORS surface.

Apply reviewed migration `0047_live_publication_actions_v1.sql` before using the owner action workspace, capture or action retention. Capture does not require the general source-crawl switch. Background after-only recovery requires the existing `NUXT_LEARNING_LOOP_ENABLED=true` as well as the live-action switch and a functioning `learning-loop:tick` task (configured every five minutes); leave crawl/training switches off when only recovery is authorized. Once private evidence exists, keep `NUXT_LEARNING_RETENTION_ENABLED=true` and the cleanup task running even if capture or the loop is paused. No switch is enabled by this implementation, and a free host's availability is not an always-on scheduler guarantee.

The existing owner intervention surface exposes `GET live-actions`, `POST live-actions/review`, `GET live-actions/:id/release` and `POST live-actions/:id/reconcile`. IDs and evidence come from the server-owned workspace; reconcile accepts only an empty object. The review endpoint never publishes or trains, and action approval is separate from subsequent model-data approval and production model activation.
